== Scope, and how this was produced

Every claim below was produced by a command run in this checkout, against
`main` at `68b2930f`. Nothing here is inferred from a status document. The
three canon repositories were read at:

What could *not* be run here, stated plainly rather than papered over:

* **GitHub Actions job logs.** `gh run view --log-failed` returns `EOF` on the
  log-download host, which this sandbox cannot reach. Each failing check was
  therefore reproduced locally from its own definition instead.
* **The Rust build.** There is no `cargo` or `rustc` here and the toolchain
  host is unreachable, so every compile-level claim (F8, F9) is read from
  source and Cargo manifests, *not* from a compiler. They are marked
  unverified-by-compilation and must be re-run on a machine with the toolchain.
* **`scripts/check-lock-sync.sh` itself.** The script fails closed without
  gawk, and gawk cannot be installed here. Its three documented clauses were
  re-implemented in Python to obtain the concrete drift list; that
  re-implementation is a diagnostic, not the shipping gate, and the gate must
  be run on the PR before the finding is called closed.
* **The code-scanning alerts API.** `gh api code-scanning/alerts` returns 403
  `Resource not accessible by integration`. Alert numbers #33 to #35 are taken
  from issue #5; their *content* was verified against source instead.

== The single root cause

*This repository was never instantiated.* It was landed from ambientops by
PR #3 as a byte copy of the template scaffold, and `just repo-init` was never
run to completion. That one omission explains five of the seven red checks
directly, and makes a sixth unsatisfiable.

The evidence is not subtle:

....
$ bash scripts/check-no-placeholders.sh .
FAIL: 90 file(s) contain unfilled {{PLACEHOLDER}} tokens
....

Ninety tracked files still carry mint-time tokens. Among them
`.github/CODEOWNERS`, whose only assignment rule is `* @` followed by the
unfilled OWNER token - so it assigns nothing to anybody; `CITATION.cff`; the
whole of `www/.well-known/` including `security.txt`;
`docs/AFFIRMATION.adoc`; `.machine_readable/compliance/reuse/dep5`; the three
agent rule files `.clinerules`, `.cursorrules` and `.windsurfrules`; and the
repo deed.

And the repo still believes it *is* the template. `CLAUDE.md` opens its
generated region with:

....
# This repo: `rsr-template-repo`  .  clade `rm-rsr-template-repo`
- Identity - uuid a5ea1382-a34c-5334-8a46-a2ebe904c810
- IS - Canonical RSR-compliant repository template
....

The deed carries the same mistake, and the template's own comment says why it
matters:

____
Before that swap existed every minted repo inherited this block's uuid and
canonical-name and told arriving agents it WAS the template.
____

That is doctrine #12 (boundaries are real) violated by inheritance rather than
by intent. Every arriving agent in this repo has been told, by the file the
estate tells agents to read first, that it is somewhere else.

== Finding register

=== F1 - The mint was never completed (90 placeholder files)

*Evidence:* `bash scripts/check-no-placeholders.sh .` exits 1, 90 files.
*Gates:* `openssf-compliance` (step "Check no unfilled placeholder tokens"),
`call-estate-audit / estate-audit` (Required Files Gate).
*Why the estate audit cannot excuse it:* cicd-suite's Required Files Gate has
a `TEMPLATE_MODE` that forgives placeholders, switched on by

....
case "${REPO_NAME##*/}" in
  *-template|*-template-repo) TEMPLATE_MODE=1 ;;
esac
....

`czech-file-knife` does not match, so the gate judges it as an instantiated
repo - correctly. The placeholders are the defect, not a false positive.

=== F7 - Swift in `cfk-ios/swift/` violates the language policy, and the policy has a hole

*Evidence:* two tracked files, `cfk-ios/swift/CfkFileProviderExtension.swift`
and `cfk-ios/swift/CfkFileProviderItem.swift`. The gate runs
`SWIFT_FILES=$(git ls-files '*.swift')` with no platform carve-out - the only
carve-out in that step is Java under `android/**/src/**`. `LANGUAGE-POLICY.adoc`
bans Swift with replacement Tauri/Dioxus and rationale "Platform lock-in",
under a heading that says "No exceptions for Kotlin/Swift."

*The tension is real, not a repo mistake.* An iOS File Provider extension is a
target Apple only lets you build as an app extension in Swift or Objective-C.
Tauri and Dioxus cannot produce one. The canon therefore forbids something the
platform requires, and the Android/Java carve-out is the precedent for how the
estate resolved exactly this shape before.

*Exemption mechanisms available here:* `.hypatia-ignore` exists;
`.hypatia-baseline.json` does not. Either can silence the check locally.

*Recommendation - the elegant arm, labelled per doctrine #15:* do **not**
silence it locally. A local exemption leaves the canon asserting something
false, and the next repo with a File Provider extension rediscovers the
problem. Take the ruling upstream as an Apple-platform-shim carve-out
paralleling the Android/Java one: Swift permitted under `*-ios/swift/**`, each
file a minimal delegating shim into the Rust core, LoC-capped as the Android
rule is. This repo's `cfk-ios` crate is already the Rust side of that seam,
which is what makes the carve-out defensible rather than a loophole.

=== F8 - Seven `unwrap()` calls on user-influenced paths

Read from source (compilation unverified, see scope):

[cols="1,2,1,2", options="header"]
|===
| File | Line | Count | Expression
| `cfk-integrations/src/agrep.rs` | 80 | 1 | `dir.to_str().unwrap()`
| `cfk-integrations/src/aria2.rs` | 26 | 1 | `output.parent().unwrap_or(...).to_str().unwrap()`
| `cfk-integrations/src/aria2.rs` | 28 | 2 | `output.file_name().unwrap().to_str().unwrap()`
| `cfk-integrations/src/aria2.rs` | 54 | 1 | `output_dir.to_str().unwrap()`

Total 7, split agrep 1, aria2 4, pandoc 2 - matching issue #5's counts

`Path::to_str` returns `None` for non-UTF-8 paths and `Path::file_name`
returns `None` for `..` and for a path ending in `..`. Both are reachable from
a CLI argument, so both are panics on attacker-shaped input in a tool whose
job is to be pointed at arbitrary filesystems.

=== WP5 - Replace the seven `unwrap()` calls with `CfkError` (MUST, local)

Fixes F8 and closes Hypatia alerts #33 to #35. Every one of the seven is on a
path built from a CLI argument, so each is a panic on hostile input in a tool
whose purpose is to be aimed at arbitrary filesystems.

The shape is uniform - `Path::to_str` and `Path::file_name` both return
`Option`, and `CfkError` already exists:

[source,rust]
----
let dir = dir.to_str().ok_or_else(|| {
    CfkError::Other(format!("non-UTF-8 path: {}", dir.display()))
})?;
----

A dedicated variant such as `CfkError::InvalidPath(PathBuf)` reads better than
`Other` and gives the CLI one place to render the message. Check `cfk-core/src/error.rs`
first; if the variant is absent, adding it is in scope for this WP.
